```
├─ _build_context_summary(user)

│  │
│  ├─ Алгоритм восстановления (RULES-BASED):
│  │  ├─ recovery_status = 'blocked' если:
│  │  │  └─ days_since == 0 или (days_since == 1 и recent_sets_3d >= 4)
│  │  ├─ recovery_status = 'fatigued' если:
│  │  │  └─ recent_sets_3d >= 6 или heavy_rpe_7d >= 3

│  │
│  ├─ Scoring мышц (FORMULA):
│  │  └─ score = (days_since * 1.4) - (recent_3d * 2.8) - (recent_7d * 0.8) - (heavy_7d * 1.5)

│  │  ├─ Priority: мышцы в рекомендации + недавно не использовались
│  │  ├─ Secondary: остальные мышцы + диверсификация

│  │

│     ├─ Если stress >= 4 → intensity_modifier = 'reduce'
```

## 🔍 ДЕТАЛЬНЫЙ РАЗБОР КАЖДОГО КОМПОНЕНТА

### 1. ЖЁСТКИЕ ПРАВИЛА (Hard-Coded Logic)

**ТЕКУЩЕЕ:**
```python
# Всё закодировано в Python constants
_EXCLUDED_MUSCLES = {'предплечья', 'кор', 'голень'}
_TIER2_MUSCLES = {'трицепс', 'бицепс', 'задние_дельты', 'трапеции', 'пресс'}
_TIER3_MUSCLES = {'икры'}

_MUSCLE_TO_PATTERNS = {
    'грудь': ['горизонтальный_жим', 'сведение'],
    'широчайшие': ['вертикальная_тяга', 'горизонтальная_тяга'],
    ...
}

_GOAL_VOLUME_GUIDANCE = {
    'масса': {'sets': '4-5', 'reps': '6-10', ...},
    'сила': {'sets': '4-6', 'reps': '3-6', ...},
    ...
}
```

**ПРОБЛЕМЫ:**
- ❌ **Ломается с новыми упражнениями** - если юзер добавит упражнение не из каталога → оно не получит паттерн
- ❌ **Нет UI для управления** - чтобы изменить tier мышцы, нужно трогать код
- ❌ **Не адаптивны** - не учитывают персональную историю пользователя
- ❌ **Жёсткие пороги** - 48 часов, 4 подхода - это глобально, для всех одинаково
- ⚠️ **Сложно расширять** - добавить новую мышцу = изменить 3 места в коде

**ПРИМЕРЫ КЕЙСОВ, КОТОРЫЕ ЛОМАЮТСЯ:**
1. Пользователь добавил "Жим гантелей" (не в fit_catalog.json) → нет паттерна → LLM выбросит его
2. Женщина хочет приоритизировать бикини-фигуру (спина, бёдра) → но Tier 1 = грудь, спина, квадрицепсы
3. Новичок хочет тренировать мышцу каждый день → blocked status не позволит (жёсткое правило 48ч)

### 2. SCORING АЛГОРИТМ (Recovery Status)

**ТЕКУЩЕЕ:**
```python
# Жёсткие пороги
if days_since == 0 or (days_since == 1 and recent_3d >= 4):
    recovery_status = 'blocked'  # Не трогай в течение 48 часов
elif recent_3d >= 6 or heavy_7d >= 3:
    recovery_status = 'fatigued'
else:
    recovery_status = 'ready'

# Scoring formula
score = (days_since * 1.4) - (recent_3d * 2.8) - (recent_7d * 0.8) - (heavy_7d * 1.5)
```

**ПРОБЛЕМЫ:**
- ⚠️ **Не адаптивны к восстановлению пользователя** - не учитывает sleep, stress, nutrition
- ⚠️ **Линейная формула** - не учитывает нелинейность (каждый подход усталости важнее)
- ⚠️ **Одинаковые коэффициенты для всех** - новичок восстанавливается иначе, чем продвинутый
- ⚠️ **Не учитывает тип упражнения** - жим ног усталит больше, чем сведение рук
- ❌ **Пороги забиты вручную** - откуда 48 часов? почему 6 подходов?

**ПРИМЕРЫ ОШИБОК:**
1. Пользователь плохо спал (2 часа), но алгоритм всё равно рекомендует blocked мышцу
2. Пользователь тренировал грудь "до отказа" 3 раза за неделю → усталость не отражена правильно
3. Новичок = advanced спортсмен имеют одинаковое время восстановления в системе

### 3. CANDIDATE EXERCISES FILTERING

**ТЕКУЩЕЕ:**
```python
# 3 категории с сортировкой
candidates_priority = []    # мышцы в recommended_focus
candidates_secondary = []   # остальные мышцы
candidates_avoid = []       # усталые мышцы

# Сортировка по daysSince (давнее) и recentCount14d
candidates_priority.sort(key=lambda item: (
    999 if item['daysSince'] is None else -item['daysSince'],
    -item['recentCount14d'],
))
```

**ПРОБЛЕМЫ:**
- ⚠️ **Не учитывает синергию** - если вчера тренировали спину, сегодня можно жим для груди (синергия)
- ⚠️ **Не учитывает баланс** - может выбрать 5 упражнений на ноги и 0 на спину (неровный split)
- ⚠️ **Нет учёта body composition** - женщине предлагает столько же ног, сколько груди
- ❌ **Жёсткая категоризация** - упражнение либо priority, либо secondary (нет middle ground)

**ПРИМЕРЫ ОШИБОК:**
1. LLM выбирает 3 упражнения на спину (все из candidates_priority) → пропускает ноги
2. Пользователь "генерирует" одну и ту же тренировку каждый раз (алгоритм детерминирован)
3. Упражнение с хорошей историей в secondary категории, но оно лучше чем priority (не может подняться)

### 4. WELLNESS INTEGRATION

**ТЕКУЩЕЕ:**
```python
# Простые IF/ELSE правила
if st >= 4:
    intensity_modifier = 'reduce'
elif s <= 2:
    intensity_modifier = 'reduce'
elif e <= 2:
    intensity_modifier = 'reduce'
elif s >= 4 and e >= 4 and m >= 4 and st <= 2:
    intensity_modifier = 'boost'

# Отправляется в prompt
"Самочувствие сегодня: {wellness_note}. Учитывай при рекомендациях."
```

**ПРОБЛЕМЫ:**
- ⚠️ **Бинарные правила** - либо boost, либо reduce, нет gradual adjustment
- ⚠️ **Не учитывает тренд** - вчера спал 8ч, сегодня 4ч (это красный флаг), но система не видит тренд
- ⚠️ **Зависит от LLM интерпретации** - коуч может их игнорировать или переусложнить
- ❌ **Не обучается** - если пользователь игнорирует рекомендации → система не адаптируется

**ПРИМЕРЫ ОШИБОК:**
1. Пользователь отмечает стресс=5, энергия=1, но LLM всё равно предлагает интенсивную тренировку
2. Недельный тренд плохого сна не учитывается (только сегодня считается)

## 🎯 СРАВНЕНИЕ: ТЕКУЩИЙ ПОДХОД vs ИИ-ПЕРВЫЙ

| **Надёжность** | ✅ Предсказуемо | ⚠️ Может галлюцинировать |
| **Стоимость** | ✅ Бесплатно | ⚠️ ~$0.03-0.10 за запрос |
| **Обучаемость** | ❌ Статично | ✅ Контекст может включать feedback |
| **Скорость** | ✅ Мгновенно | ⚠️ 2-5 сек на запрос |
| **Аудит** | ✅ Понятно почему | ⚠️ Чёрный ящик |

```python
# models/coach_config.py

class MuscleConfig(Base):
    __tablename__ = 'coach_muscle_config'
    
    user_id: int = foreign_key('users')
    muscle_name: str  # "грудь", "спина", и т.д.
    tier: int  # 1, 2, 3, null (excluded)
    min_days_between_training: int = 2  # вместо hard-coded 48h
    target_volume_week_sets: int | None  # сколько подходов в неделю оптимально
    notes: str  # "женский/мужской приоритет" и т.д.
    created_at: datetime
    updated_at: datetime
    
    def to_dict(self) -> dict:
        return {
            'muscle': self.muscle_name,
            'tier': self.tier,
            'minDaysBetween': self.min_days_between_training,
            'targetVolume': self.target_volume_week_sets,
        }


class MovementPattern(Base):
    __tablename__ = 'coach_movement_patterns'
    
    user_id: int = foreign_key('users')
    pattern_name: str  # "горизонтальный_жим", "вертикальная_тяга"
    target_muscle: str
    exercise_examples: str  # JSON: ["Жим лежа", "Жим на тренажёре"]
    priority: int  # 1-5 (как часто использовать)
    notes: str
    
    def to_dict(self) -> dict:
        return {
            'pattern': self.pattern_name,
            'targetMuscle': self.target_muscle,
            'priority': self.priority,
        }


class VolumeGuidance(Base):
    __tablename__ = 'coach_volume_guidance'
    
    user_id: int = foreign_key('users')
    goal: str  # "масса", "сила", "похудение", "поддержание"
    ideal_sets_min: int
    ideal_sets_max: int
    ideal_reps_min: int
    ideal_reps_max: int
    rest_seconds: int
    notes: str  # "базовые движения в приоритете"
    is_default: bool = False  # используется если goal не установлена
```

## 📊 СРАВНЕНИЕ: СТОИМОСТЬ vs ВЫИГРЫШ

### ВАРИАНТ 1: Ничего не менять
```
СТОИМОСТЬ:
  - Разработка: 0 часов
  - API: $0 (локальная логика)
  - Maintenance: минимальная
  
ВЫИГРЫШ:
  - Работает как есть
  - Пользователи довольны
  
ПОТЕРИ:
  - Не масштабируется
  - Жёсткие пороги для всех
  - Нельзя персонализировать
```

### ВАРИАНТ 2: Гибридный (рекомендуется)
```
СТОИМОСТЬ:
  - Разработка: ~40-50 часов (1-2 недели)
  - БД миграция: 5 часов
  - API: $0 (LLM вызовы как раньше)
  - Maintenance: чуть выше (таблицы конфига)
  
ВЫИГРЫШ:
  - Масштабируемость (новые мышцы → БД запись)
  - Гибкость (UI для настроек)
  - Можно персонализировать (different users → different configs)
  - Все контролируется через LLM prompt
  - Easier to debug
  
ПОТЕРИ:
  - Чуть медленнее (одна доп query на context)
  - Нужно документировать новые таблицы
```

### ВАРИАНТ 3: Полностью ИИ-первый
```
СТОИМОСТЬ:
  - Разработка: ~100-150 часов (3-4 недели)
  - БД миграция: 10 часов
  - API: $0.03-0.10 за генерацию (~$30K/месяц для 100K пользователей)
  - Maintenance: высокая (нужны safeguards)
  - Testing: интенсивное (hallucinations, corner cases)
  
ВЫИГРЫШ:
  - Максимальная персонализация
  - Обучается от feedback
  - Может рекомендовать новые упражнения
  - Полностью адаптивно
  
ПОТЕРИ:
  - Дорого
  - Медленнее (2-5 сек вместо instant)
  - Может ошибиться (hallucinate упражнения которых нет)
  - Сложно контролировать
```

# 📊 ДЕТАЛЬНОЕ ОПИСАНИЕ ФУНКЦИЙ Alpha4Sport

---

## 1️⃣ АУТЕНТИФИКАЦИЯ И ПРОФИЛЬ

### 🔐 Регистрация / Логин / Bootstrap

**КАК РАБОТАЕТ:**
- Пользователь отправляет email + пароль
- Пароль хешируется через bcrypt (один раз, при регистрации)
- Создаётся запись в БД с уникальным email (case-insensitive)
- JWT токен генерируется и возвращается на фронт
- При первой регистрации автоматически загружается каталог упражнений

**СТАТУС:** ✅ **Полностью реализована**

**ЗАВИСИМОСТИ:**
- SQLAlchemy ORM, bcrypt, JWT
- Таблица `users` с уникальным индексом на email

**ПРОБЛЕМЫ / ОГРАНИЧЕНИЯ:**
- ❌ Нет восстановления пароля (forgot password)
- ❌ Нет двухфакторной аутентификации
- ❌ Нет логирования попыток входа (для безопасности)
- ⚠️ Email не валидируется отправкой confirmation link
- ⚠️ Пароль не проверяется на сложность (минимум требований не установлен)

**ЮЗАБЕЛЬНОСТЬ:** 🟡 Базовая, но небезопасная без доп. проверок

---

### 👤 Профиль пользователя (получить текущего пользователя)

**КАК РАБОТАЕТ:**
- GET запрос с JWT токеном в Authorization заголовке
- Парсится payload токена → извлекается user_id
- Выполняется SELECT из БД с этим user_id
- Возвращаются: id, email, display_name (или сгенерированное из email), avatar_url

**СТАТУС:** ✅ **Полностью реализована**

**ЗАВИСИМОСТИ:**
- JWT парсер, таблица users, таблица user_profiles (для аватара)

**МЕХАНИКА ОТОБРАЖАЕМОГО ИМЕНИ:**
```python
# Если display_name не установлен → генерируется из email
user_email = "john.doe@example.com"
# john.doe → john doe → John Doe
```

**ПРОБЛЕМЫ:**
- ⚠️ Нет кэширования профиля (каждый запрос → БД)

### 🎨 Загрузка аватара

**КАК РАБОТАЕТ:**
1. Клиент отправляет multipart-form файл
2. Валидируется: расширение (.jpg, .png, .webp), размер (≤5МБ)
3. Генерируется уникальное имя: `{user_id}_{uuid4}{extension}`
4. Файл сохраняется в `/uploads/avatars/`
5. Путь сохраняется в БД: `user.avatar_path = "avatars/1234_uuid.jpg"`
6. При каждом запросе профиля → URL = `/uploads/{avatar_path}`

**СТАТУС:** ✅ **Полностью реализована**

**ПРОБЛЕМЫ:**
- ⚠️ Нет сжатия/оптимизации изображений (может быть тяжелым)
- ⚠️ Нет удаления старого аватара при загрузке нового
- ❌ Нет обработки EXIF данных (приватность)
- ⚠️ Путь хранится в БД, а не восстанавливается с диска
- ⚠️ Нет защиты от RCE через заголовки файла (только по расширению)

**ЮЗАБЕЛЬНОСТЬ:** 🟡 Работает, но неполная обработка

### 📋 Фитнес профиль (цели, опыт, травмы)

**КАК РАБОТАЕТ:**
- Сохраняются в таблице `user_profiles` (один запись per пользователя)
- Поля: goals (строка, разделённая запятыми), experience, gender, injuries, days_per_week
- PUT запрос → upsert (если нет записи, создаётся новая)
- Валидация целей: только из набора {масса, сила, похудение, поддержание}

**СТАТУС:** ✅ **Полностью реализована**

**ПРОБЛЕМЫ:**
- ⚠️ Goals сохраняются как comma-separated string (не нормализованная таблица)
- ⚠️ Нет валидации по длине text полей (injuries может быть 10000+ символов)

## 2️⃣ ТРЕНИРОВКИ

### 🏋️ Создать тренировку

**КАК РАБОТАЕТ:**
```
POST /workouts с payload:
{
  name: "Жим лежа",
  notes: "Тяжелый день",
  started_at: "2025-03-10T10:00:00Z",
  finished_at: null,  // или время завершения
  exercises: [
    {
      position: 1,
      exercise_name: "Жим штанги лежа",
      catalog_exercise_id: 42,  // опционально
      sets: [
        {position: 1, reps: 10, weight: 100, set_type: "work", rpe: 8}
      ]
    }
  ]
}
```

**МЕХАНИКА:**
1. Создаётся Workout запись с user_id и временем
2. Для каждого упражнения:
   - Если указан catalog_exercise_id → валидируется его существование и принадлежность пользователю
   - Если нет → используется exercise_name как-есть
3. Для каждого подхода создаётся ExerciseSet
4. **Если finished_at не null:**
   - Автоматически создаётся AccountEvent (событие в ленте активности)
   - Вызывается ProgressionService.recalculate_for_user → пересчитывается весь прогресс
5. При пересчёте прогресса:
   - Анализируются все завершённые тренировки
   - Ищутся новые personal records (PR)
   - Начисляются XP очки
   - Проверяются достижения
   - Пересчитываются streaks

**СТАТУС:** ✅ **Полностью реализована**

**ЗАВИСИМОСТИ:**
- 3 таблицы: workouts, workout_exercises, exercise_sets
- ProgressionService (сложный пересчёт)
- AccountEventService (логирование)

**ПРОБЛЕМЫ:**
- ⚠️ Если workout.finished_at = null → прогресс не пересчитывается (зависает в черновиках?)
- ⚠️ Нет валидации на макс количество упражнений в тренировке
- ⚠️ Нет валидации weight/reps на логику (negative values?)
- ⚠️ set_type может быть любым значением (не из фиксированного набора)

**ЮЗАБЕЛЬНОСТЬ:** 🟢 Работает хорошо, но неполная валидация

**КАК РАБОТАЕТ:**
- SELECT * FROM workouts WHERE user_id = ? ORDER BY started_at DESC
- Подгружаются все упражнения и подходы (joinedload)
- Возвращается список с полной иерархией

**СТАТУС:** ✅ **Полностью реализована**

**ПРОБЛЕМЫ:**
- ⚠️ Нет пагинации (если 1000+ тренировок → весь список за раз)
- ⚠️ Может быть медленно для пользователей с большой историей

### 🔄 Начать тренировку из шаблона

**КАК РАБОТАЕТ:**
1. POST /workouts/from-template/{template_id}
2. Находится шаблон по ID + user_id
3. Создаётся новая тренировка с:
   - name, notes из шаблона
   - started_at = NOW (текущее время)
   - finished_at = null (не завершена)
4. Для каждого упражнения в шаблоне:
   - Копируется exercise_name, catalog_exercise_id
   - Автоматически создаётся N подходов (target_sets из шаблона)
   - Каждый подход: weight = target_weight, reps = 0, set_type = 'work'
5. Пересчитывается прогресс

**СТАТУС:** ✅ **Полностью реализована**

**ИНТЕРЕСНАЯ ДЕТАЛЬ:**
- Подходы создаются с reps=0, weight из шаблона
- Пользователь заполняет реальные reps после тренировки

**ПРОБЛЕМЫ:**
- ⚠️ target_reps из шаблона НЕ используется (зачем он тогда?)

---

### 📈 История упражнения (последние значения)

**КАК РАБОТАЕТ:**
- GET /workouts/previous/{exercise_name}?limit=5
- Нормализует имя упражнения (lowercase, ё→е)
- SELECT из exercise_sets с условиями:
  - WHERE workout.user_id = ? 
  - AND normalized_name = normalized_input
  - AND set_type != 'warmup'
  - ORDER BY workout.started_at DESC, set.position DESC
  - LIMIT 5
- Возвращает: [{date, weight, reps}]

**СТАТУС:** ✅ **Полностью реализована**

**ОСОБЕННОСТЬ:**
- Сортировка по position DESC → берётся последний подход в упражнении (обычно наиболее усталый)

---

### ✏️ Редактировать / ❌ Удалить тренировку

**РЕДАКТИРОВАНИЕ:**
- PUT /workouts/{workout_id}
- Заменяется: name, notes, started_at, finished_at
- Полностью заменяются упражнения (hydrate_exercises → clear + add)
- Пересчитывается прогресс

**УДАЛЕНИЕ:**
- DELETE /workouts/{workout_id}
- Удаляются все связанные AccountEvent'ы (events, records)
- Cascade удаление упражнений и подходов
- Пересчитывается прогресс

**СТАТУС:** ✅ **Полностью реализована**

**ПРОБЛЕМЫ:**
- ⚠️ При удалении упражнения → полностью перестраивается список (нет partial edit)
- ⚠️ При пересчёте прогресса после edit/delete → может быть медленно для больших данных

2. Вызывается `ensure_seed_catalog(db, user_id)`:

**СТАТУС:** ✅ **Полностью реализована**

**ВНУТРЕННИЕ ДЕТАЛИ:**
- Встроенный каталог в JSON с полной информацией о мышцах
- При первом запросе пользователя → все упражнения скопированы в личный каталог

**ПРОБЛЕМЫ:**
- ⚠️ `ensure_seed_catalog` вызывается на каждом запросе (даже если уже загружено)
- ⚠️ Встроенный каталог жёстко закодирован в /docs/fit_catalog.json

### ➕ Создать упражнение

**КАК РАБОТАЕТ:**
```
POST /exercises:
{
  name: "Жим штанги лежа",
  primary_muscle: "грудь",
  secondary_muscles: ["передние_дельты", "трицепс"]
}
```

1. Нормализуется имя (trim, lowercase)

4. Валидируются мышцы:

   - secondary_muscles не должны пересекаться с primary
5. Создаётся ExerciseCatalog + ExerciseSecondaryMuscle записи

**СТАТУС:** ✅ **Полностью реализована**

**ЗАВИСИМОСТИ:**
- Таблицы: exercise_catalog, exercise_secondary_muscles
- Валидатор muscles (жёсткий набор)

**ПРОБЛЕМЫ:**
- ⚠️ slug не используется нигде (зачем вычислять?)
- ⚠️ Нет проверки на похожие имена (user может создать "Жим" и "жим" - это будут разные)

## 6️⃣ ПРОГРЕСС И СТАТИСТИКА

### 📈 История упражнения (детальная) + Недельный объём + Тренд веса

**КАК РАБОТАЕТ:**

#### История упражнения (для графика):
```
GET /progress/exercise/{exercise_name}
```
- Список всех выполнений упражнения с date, weight, reps
- Рассчитывает estimated_1rm для каждого (Brzycki formula: weight * (1 + reps/30))
- Используется для построения графика в UI

#### Недельный объём:
```
GET /progress/weekly-volume
```
- GROUP BY week (date_trunc('week', started_at))
- SUM(weight * reps) для всех подходов в неделе
- Возвращает: [{week_start, volume}]

#### Тренд веса:
```
GET /progress/bodyweight-trend?days=90
```
- SELECT FROM body_entries WHERE entry_date >= (today - 90 дней)
- Возвращает: [{date, weight_kg}]
- Используется для графика

**СТАТУС:** ✅ **Полностью реализована**

**ПРОБЛЕМЫ:**
- ⚠️ Нет интерполяции (missing dates → пробелы в графике)
- ⚠️ 1RM формула упрощённая (есть и другие)

---

### 🎯 Профиль прогрессии (сложная система)

**КАК РАБОТАЕТ:**

Это самая сложная функция. При каждой завершённой тренировке вызывается `ProgressionService.recalculate_for_user()`:

1. **Пересчитываются личные рекорды (PR) по упражнениям:**
   - best_weight (максимальный вес)
   - best_1rm (максимальная расчётная 1РМ)
   - best_volume (максимальный общий объём за тренировку)
   - best_reps (максимум повторений за подход)

2. **Начисляются XP очки в зависимости от типа достижения:**
   ```
   NEW PR (weight/1rm/reps/volume) → 8-10 XP
   Завершённая тренировка → 10 XP (новая система, было 20)
   Идеальная неделя (≥4 тренировок) → 30 XP
   Идеальный месяц (≥3 идеальные недели) → 100 XP
   Milestone (10/25/50 тренировок) → 30-100 XP
   ```

3. **Уровень рассчитывается по XP:**
   ```
   Level 1: 0-150 XP (Новичок)
   Level 2: 150-400 XP (Идущий)
   Level 3: 400-800 XP (Практик)
   ...
   Level 9: 5300+ XP (Архитектор силы)
   Level 10+: каждые 1100+ XP → +1 уровень
   ```

4. **Считаются streaks:**
   - current_streak: количество дней подряд с тренировками
   - best_streak: максимальный streak в истории

5. **Создаются события (ProgressRecordEvent, ProgressRewardEvent):**
   - Уникальные ключи предотвращают двойное начисление XP

**СТАТУС:** ✅ **Полностью реализована**

**ЗАВИСИМОСТИ:**
- 4 таблицы: user_progressions, progress_reward_events, progress_exercise_records, progress_record_events
- Сложная бизнес-логика с множеством условий

**ПРОБЛЕМЫ:**
- ⚠️ **XP был переоценен** (было 20 за тренировку, стало 10) → но старые рекорды остались на OLD систему!
  - Дата: 2026-03-20
  - Нужна миграция (recalculate_all.py), но она может быть не запущена
- ⚠️ Streak не учитывает больничные листы (sick leaves) → может быть unfair
- ⚠️ При удалении тренировки → пересчитывается всё (может быть медленно)
- ⚠️ Нет кэша → каждый запрос профиля = пересчёт с нуля

**ЮЗАБИЛЬНОСТЬ:** 🔴 Сложная система, много edge cases

### 🏥 Больничный лист (sick leave)

**КАК РАБОТАЕТ:**
```
POST /progression/sick-leaves:
{
  startDate: "2025-03-01",
  endDate: "2025-03-07",
  reason: "болезнь"  // из набора: болезнь, травма, восстановление, командировка, другое
}
```

1. Валидируется: start_date <= end_date
2. Создаётся SickLeave запись со статусом 'active'
3. При пересчёте streak → дни в диапазоне [start_date, end_date] пропускаются
4. Может быть отменён: POST /sick-leaves/{id}/cancel

**СТАТУС:** ✅ **Полностью реализована**

**ПРОБЛЕМЫ:**
- ⚠️ Больничный НЕ влияет на calculation текущего дня (создаёшь в день, но уже потерял streak?)
- ⚠️ Нет ограничения на перекрывающиеся больничные

## 8️⃣ ИИ-КОУЧ (CLAUDE API)

### 🤖 Чат с коучем

**КАК РАБОТАЕТ:**
```
POST /coach/chat:
{
  messages: [{role: "user", content: "Как мне прогрессировать в жиме?"}],
  wellness_entries: [{...}],  // опционально
  save_history: true          // сохранить в БД?
}
```

1. Собирается контекст пользователя:
   - История тренировок
   - Прогресс упражнений
   - Wellness данные
   - Профиль пользователя (цели, опыт)

2. Формируется системный промпт с инструкциями (на русском)

3. Отправляется запрос на Claude API (Anthropic):
   - Используется модель из env (обычно claude-3.5-sonnet)
   - Streaming поддерживается

4. Если save_history=true → сохраняется обмен в БД (CoachChatMessage)

5. Коуч использует JSON-каталог упражнений для умных рекомендаций

**СТАТУС:** ✅ **Полностью реализована**

**ЗАВИСИМОСТИ:**
- Claude API (требует ANTHROPIC_API_KEY в env)
- Таблица coach_chat_messages
- /docs/fit_catalog.json (каталог упражнений с метаданными)

**МЕХАНИКА ГЕНЕРАЦИИ ТРЕНИРОВКИ:**
```
POST /coach/generate-workout:
{
  intensity_title: "Средняя",
  min_exercises: 5,
  max_exercises: 8,
  user_notes: "Завтра много работы",
  wellness_entries: [{...}]
}
```

1. ИИ анализирует:
   - Целевые мышцы (из профиля + диверсификация)
   - Уровень интенсивности
   - Wellness (если очень плохое самочувствие → лёгкая тренировка)
   - Историю тренировок (не повторяет недавно)

2. Возвращает полную программу с:
   - Списком упражнений
   - Подходами, повторениями, весом
   - Notes для каждого упражнения

**СТАТУС:** ✅ **Полностью реализована**

**ПРОБЛЕМЫ:**
- ❌ API ключ должен быть в env (нет обработки ошибки "ключ не установлен" → 500 error)
- ⚠️ Нет rate limiting (пользователь может спамить запросы)
- ⚠️ Нет логирования затрат на API (сколько токенов потрачено?)
- ⚠️ История диалогов не используется для контекста в следующих диалогах
- ⚠️ Коуч знает историю пользователя, но не знает о других пользователях (для сравнения)

**ЮЗАБИЛЬНОСТЬ:** 🟢 Работает хорошо, но нужна защита от abuse
